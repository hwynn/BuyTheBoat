## Class hierarchy at a glance

```
TransactionLogBook
└─ log_pages: TransactionLogPage[]
   └─ account_pages: AccountTransactionPage{}      (one per account name)
      ├─ finance_patterns: FinancialPattern[]
      ├─ earmark_patterns: EarMarkPattern[]
      ├─ initial_snapshot: BalanceSnapshot           (the one snapshot with no date)
      └─ balance_record: {Date: BalanceSnapshot}
         └─ BalanceSnapshot (one per date that has an event)
            ├─ actual_transactions: ActualTransaction[]
            ├─ expected_transactions: ExpectedTransaction[]
            ├─ earmark_events: EarMarkEvent[]
            └─ fund_jars: FundJar[]
```

`FinancialPattern` and `EarMarkPattern` are templates that *generate* `ExpectedTransaction` and `EarMarkEvent` instances (respectively) onto specific dates according to an `rrule`. `ActualTransaction` is the odd one out — it isn't generated by a pattern, it's recorded from real-world bank activity and then optionally *paired* to an `ExpectedTransaction`.

## Classes

### TransactionLogBook
The root container. Owns every `TransactionLogPage` in the budget.

| Property | Type | Mandatory | Meaning |
|---|---|---|---|
| `page_length` | Int | — | Number of months a `TransactionLogPage` spans. |
| `log_pages` | `TransactionLogPage[]` | — | Cannot be null; can be an empty list. Pages are ordered — "page X is immediately before page Y." |

**Key methods** (from `psuedo_functions.txt`):
- `find_page_at_date(p_date)` — returns the `TransactionLogPage` whose `[start_date, end_date]` contains the given date.
- `add_bulk_transactions(p_account_name, p_files)` — imports a list of transaction files (order/overlap not assumed), routing each file's transactions to the correct log page/account page by date, splitting a file across pages if it spans a page boundary.
- `ad_hoc_initial_balance_adjustment(p_account_name, p_date, p_amount)` — a hard reset: sets a new starting balance at a given account+date and marks every earlier `AccountTransactionPage` for that account as expired (after user confirmation). Effectively restarts the log book's history for that account.
- Creates/deletes `TransactionLogPage`s; when a balance record change happens in the past, deletes and recreates the affected balance snapshots and cascades the update forward into future pages.

### TransactionLogPage
*Early notes (`fakexmltest.txt`, March 2021) call this page's bounds `last_date` and its lock flag `archived` — both were later renamed to `end_date` and `expired` (see [Naming quirks](#naming-quirks--open-questions)).*

> "A document set up for a designated period of time. Used for a period of time between two fixed dates. Holds a schedule of expected transactions." — `class documentation.ods`

| Property | Type | Mandatory | Meaning |
|---|---|---|---|
| `start_date` | Date | Yes | Cannot be None; must be before `end_date`. |
| `end_date` | Date | Yes | Cannot be None; must be after `start_date`. |
| `account_pages` | `AccountTransactionPage{}` | Yes | Cannot be None; can be an empty dictionary/set. Keyed by account name. |

### AccountTransactionPage
The workhorse class — one per account, per `TransactionLogPage`. Holds the actual schedule of money movement for that account over that period, plus the running calculations (free amount, safety cushion, fund jars).

| Property | Type | Mandatory | Meaning |
|---|---|---|---|
| `account` | String (unique) | Yes | Matches the account name used in exported Mint transaction files. |
| `start_date` | — | Yes | Inherited bounds, same rules as the page. |
| `end_date` | — | Yes | |
| `expired` | Bool | — | An expired page can't be edited, and no information can cascade outside it. A page becomes expired when it's old enough, or when its data is known-inaccurate and can't be corrected. |
| `current_free_amount` | Float | — | How much is free to spend *right now* without dipping into the safety cushion or goal savings. **Cannot be computed by a cascade** (so it can't feed anything else a cascade computes). Accounts for `current_unpaid_expected` — unless money for that unpaid bill is already parked in a fund jar, in which case the fund jar already covers it. |
| `current_unpaid_expected` | Float | — | Total amount of past, unfulfilled `ExpectedTransaction`s — money expected to move any day now. Feeds into `current_free_amount`. |
| `current_safety_cushion` | Float | — | How much is *currently* set aside as a safety cushion (may be less than the ideal). The ODS description embeds a further note dropped from earlier passes of this doc: "The priority value of maintaining our safety balance. We might be saving for something availible for only a limited time and is so important it's worth dipping into our safety balance for. Automatically set, but theoretically we could let the user change this." *(verbatim, sic)* |
| `ideal_safety_cushion` | Float | Yes | How much the user *wants* kept as a safety cushion. Cannot be negative. Higher values shrink `current_free_amount`. |
| `safety_priority` | Int | Yes | The safety cushion's priority, compared against `FinancialPattern.priority`/`EarMarkPattern` priorities when funds are scarce. No finance pattern may share this exact value. |
| `finance_patterns` | `FinancialPattern[]` | — | |
| `earmark_patterns` | `EarMarkPattern[]` | — | |
| `initial_snapshot` | `BalanceSnapshot` | Yes | The one `BalanceSnapshot` with no date — the starting point everything else in the page is calculated from. Gets revised repeatedly before the period's first real day arrives. |
| `balance_record` | `{Date: BalanceSnapshot}` | — | One entry per date that has at least one event. Look-ahead horizon to confidently answer "how much will I have free on date X" is roughly 3 months. |
| `applied_date` | Date | — | Date of the last time "consciously-applied" calculations ran (`FundJar.milestone_amount`, `current_free_amount`, `current_unpaid_expected`, `current_safety_cushion`). |

**Key methods** (from `psuedo_functions.txt`):
- `cascade_page_balance_record(self, start_date=None)` — **the central recalculation engine.** Assumes every balance snapshot at/after a date is wrong and everything before it is right; walks forward from the last correct snapshot, recomputing each one from events/transactions along the way. Does not create new snapshots (see `adjust_snapshots`) or touch the initial snapshot. Returns the final snapshot's values, which `set_initial_balance_snapshot` uses to seed the *next* page.
- `set_initial_balance_snapshot(self, p_full_amount, p_free_amount, p_expected_amount, p_fund_jars)` — sets up `initial_snapshot`.
- `are_snapshots_adjusted()` / `adjust_snapshots(p_trigger_update=true)` — the former checks whether a `BalanceSnapshot` exists on every date that has an earmark/expected/actual event and nowhere else; the latter fixes it (creates missing ones, deletes orphaned ones, sorts the list), then optionally triggers a cascade.
- `earmark_ids_on_day(p_date)` / `earmarks_on_day(p_date)` — which repeated earmarks (by finance_id, then as full objects) should exist on a date, per the `EarMarkPattern`s.
- `expected_transaction_ids_on_day(p_date)` / `expected_transactions_on_day(p_date)` — same idea for `FinancialPattern` → `ExpectedTransaction`.
- `page_runoff_data()` — bundles everything the *next* `AccountTransactionPage` needs to start (finance patterns, earmark patterns, closing balance snapshot, fund jars).
- `force_expire()` — marks the page expired; for any `ExpectedTransaction`/`ActualTransaction` paired to something *outside* this page, strips the pairing but leaves the transaction itself untouched.
- `find_actual(p_date)` / `find_expected(p_date, p_finance_id)` — lookups within the page's transactions.
- `earmark_exists(...)` / `find_earmark(...)` — lookups for a specific repeated-or-isolated earmark by finance_id + date.
- `is_deallocation_day()` — true if total actual transactions for the day exceed the free funds available (see [Deallocation day](#domain-vocabulary)).
- `calculate_deallocation_earmarks()` — computes the `(finance_id, amount)` pairs that need implicit earmarks on a deallocation day, without creating them.
- `reverse_implicit_earmarks(p_earmark_date, p_finance_id=None)` — on a date (optionally scoped to one finance_id), converts isolated earmarks back to their explicit amounts and deletes any that net to zero.
- `pair_actual_event(p_finance_id, p_date)` / `unpair_actual_event(p_finance_id, p_date)` — pairs/unpairs an `ActualTransaction` with an `ExpectedTransaction`, implicitly creating/reversing a fund-jar-withdrawal earmark to match.
- `add_bulk_transactions(p_transactions)` — imports a batch of `ActualTransaction`s (see `TransactionLogBook.add_bulk_transactions`).
- `ScanForMatchs()` — searches loose `ActualTransaction`s for an unpaired `ExpectedTransaction` to match, possibly reaching into adjacent transaction logs.

### FinancialPattern
A template that generates repeated `ExpectedTransaction`s — a bill or paycheck.

> "The pattern id of financial patterns in two different event planners should match if they have the same: source, rrule (excluding start date), amount. Changes cascaded into past stop at expired pages." — `class documentation.ods`

| Property | Type | Mandatory | Meaning |
|---|---|---|---|
| `finance_id` | Int (unique) | Yes | Cannot be None. Uniquely identifies this pattern; threads through `ExpectedTransaction`, `EarMarkPattern`, `EarMarkEvent`, and `FundJar`. |
| `source` | String (unique) | — | Cannot be None (per the base assumption files — see [Naming quirks](#naming-quirks--open-questions) for a numbering caveat). The exact string expected in the bank/Mint transaction description, used for automatic pairing. No two patterns should share a source. If manually paired, the pattern's source gets updated to match the actual transaction's source. |
| `date_pattern` | rrule | Yes | Which dates generate `ExpectedTransaction`s, and for how long. Long-lived patterns span many `AccountTransactionPage`s. |
| `amount` | Float | Yes | The `expected_amount` given to generated transactions. Changes cascade into the future. |
| `amount_tolerance` | Float Pair | — | Default `[0,0]`. Passed down to generated transactions. Per the ODS: "Changes to this should cascade into the future" (the same clause `amount` carries; `date_tolerance` notably lacks it). |
| `date_tolerance` | Float Pair | — | Default `[0,0]`. Passed down to generated transactions. |
| `priority` | Int | Yes | Which goals get funded first when money is short. 1 = lowest; higher = higher priority. Can't tie `AccountTransactionPage.safety_priority`. |
| `mandatory` | Bool | Yes (defaults true if `amount` is negative) | Is this a bill you *have* to pay? Mandatory transactions outrank non-mandatory ones. Changes cascade into both the past and future. |
| `notifications` | Bool | — | Whether to remind the user to make a manual transaction for this pattern. The ODS leaves an open design question here, verbatim: "Note: we might want to be able to warn the user ahead of time to pay these. But we would need to know when to do this." |
| `description` | String | — | Human-readable name. |

### EarMarkPattern
A template that generates repeated `EarMarkEvent`s — recurring contributions toward a single goal (a specific `ExpectedTransaction`'s `finance_id`).

> "EarmarkEvents will work like expected events. The user will have to change this pattern to stay on track with a goal if they fall behind. EarMarks all have priorities — set by the finance pattern of the expected transaction these earmarks are saving for." — `class documentation.ods`

*The ODS purpose statement carries one more clause dropped from the quote above: "Changes cascaded into past stop at expired pages." (the same rule `FinancialPattern`'s quote preserves).*

| Property | Type | Mandatory | Meaning |
|---|---|---|---|
| `finance_id` | Int (unique) | Yes | The `finance_id` of the `ExpectedTransaction` being saved for. One earmark pattern per goal, one goal per earmark pattern — this is the only link between them. |
| `date_pattern` | rrule | Yes | Can't generate dates past the goal's own `FinancialPattern` rrule. New patterns default to suggesting the user's payday rrule. |
| `amount` | Float | Yes | The `expected_amount` given to generated earmarks. |

| Property | Type | Mandatory | Meaning |
|---|---|---|---|

| `occurred_date` | Date | Yes | Cannot be in the future — a user can't record a transaction in advance. |
| `paired_finance_id` | Int | — | The `finance_id` of the `ExpectedTransaction` this is paired to. If `paired_expected_date` is None, this must also be None. |
| `paired_expected_date` | Date | — | The `expected_date` of the paired `ExpectedTransaction`. |
| `made_in_bulk` | Bool | Yes | Whether this came from a batch import. |

### ExpectedTransaction
A single, discrete anticipated event on a specific date — a bill's due date, a paycheck date.

> "An expected transaction is a singular, discrete event in a transaction log page. It is normally created after the current date. It is completely editable (except for `finance_id`, and `fulfillment` is changed by the system). If it exists in an ACTIVE page, it has an associated financial pattern — true even for one-time payments. No two expected transactions of the same `finance_id` can occur on the same day. If it has a `finance_id`, it's a repeated expected transaction (even if it only happens once); a manually-created one-off is called an 'isolated' expected transaction, but the system still synthesizes a `FinancialPattern` for it so it always has a `finance_id`." — `class documentation.ods` (paraphrased/condensed)

| Property | Type | Mandatory | Meaning |
|---|---|---|---|
| `finance_id` | Int | Yes | Which `FinancialPattern` generated this. |
| `expected_date` | Date | Yes | |
| `cancelled` | Bool | Yes | If true, the transaction is ignored. `paired_amount`/`paired_actual_date` must both be None if cancelled. |
| `paired_amount` | Float | — | Mirrors the paired `ActualTransaction.amount`. None unless `paired_actual_date` is also set. |
| `paired_actual_date` | Date | — | Mirrors the paired `ActualTransaction.occurred_date`. None unless `paired_amount` is also set. |
| `expected_amount` | Float | Yes | Comes from the `FinancialPattern.amount` for repeated transactions. |
| `amount_tolerance` | Float Pair | Yes | How much variance before a deviation warning fires. Defaults from the `FinancialPattern`. |
| `date_tolerance` | Float Pair | Yes | Same idea, for date variance. Defaults from the `FinancialPattern`. |

### EarMarkEvent
*Also referred to in places just as "earmark" — the ODS explicitly notes these are synonyms.* Moves money into (or, if negative, out of) a `FundJar` on a specific day.

> "Only an actual event can implicitly pull money out of a fund jar. Earmarking is first come first served — even if the highest-priority earmark doesn't have enough money and other fund jars have extra, we will not implicitly draw on that extra to cover the shortfall... We will never implicitly add to a fund jar's expected amount; implicit isolated earmarks are only ever negative (a response to actual transactions overdrawing free funds)." — `class documentation.ods` (condensed)

*Editorial note (added 2026-07-10, per the original author — the docs themselves never state the reasoning):* the "only an actual event can implicitly pull money out" rule exists because **actual transactions were meant to be the driving force that triggers a deallocation day** — a real transaction removing money that had been allocated was to be the only reason funds get recalculated implicitly. This presumed actual transactions would exist. Recorded here for future reference: until actual-transaction import is real, the C# rewrite operates under the **assumed-pairing** philosophy (see `MyMoneyForecast/planning/05-original-structure-restructure.md`) — expected transactions stand in as the trigger, on the assumption their pairings will happen.

*Two rules from the ODS's fuller passage, condensed away above:* an earmark pattern cannot create more than one event on a single day ("No two repeated earmarks with the same finance_id can occur on the same day"), and implicitly-created isolated earmarks merge into existing isolated earmarks the same way manually-added ones do.

| Property | Type | Mandatory | Meaning |
|---|---|---|---|
| `finance_id` | Int | Yes, but can be None | The goal's `finance_id`. None = this earmark is for the safety cushion. This is the *only* way an earmark's `EarMarkPattern` gets identified — hence only one earmark pattern is allowed per `finance_id`. The ODS gives the reason, verbatim: "because if two earmark events of the same finance_id fall on the same day, we would have to split actual_amount between the two of them, and that's way too complicated." |
| `earmark_date` | Date | Yes | Every earmark needs a date, which is what lets them be created manually at will. |
| `repeated_earmark` | Bool | Yes | True if generated by an `EarMarkPattern`; false for manual or implicit (actual-transaction-triggered) earmarks. |
| `expected_amount` | Float | Yes | How much this event is supposed to move. Immutable for repeated earmarks (make an isolated earmark on the same day instead); mutable for isolated ones. A negative amount pulls money *out* of the jar into free balance. A second isolated earmark for the same `finance_id`/day just adds onto the first's amount rather than creating a new one. |
| `explicit_amount` | Float | Only for isolated | How much was added *explicitly* by the user (as opposed to implicitly, by the system reacting to an actual transaction). Used to undo implicit changes. |
| `actual_amount` | Float | — | How much actually moved, set only once the date has occurred — one of the last things a cascade update computes. If exactly one earmark event exists for a fund jar on a day, its `actual_amount` = that fund jar's `current_amount` today minus yesterday's. If both a repeated *and* isolated earmark exist for the same jar/day, only the repeated one gets an `actual_amount` — the isolated one gets None. |

### BalanceSnapshot
Everything that happened on one specific day, for one `AccountTransactionPage`. There is also exactly one dateless instance per page (`initial_snapshot`).

> "This holds all transactions and earmarks occuring on a specific day.
> This shows how much money we have on a specific day.This holds all the fund jars, showing how much money we have set aside for various goals at this date." — `class documentation.ods` *(verbatim, sic — added 2026-07-10; earlier passes of this doc only paraphrased it)*

*Per the original author (2026-07-10): a snapshot's properties are where the per-day answers to the project's core questions live — how much money exists (`full_amount`/`expected_amount`), what's allocated to what and whether each goal is on track (`fund_jars`, cross-referenced against milestones), and what's actually free (`expected_free_amount`/the page's `current_free_amount`). The UI is meant to be layered views of this onion at different scales.*

| Property | Type | Mandatory | Meaning |
|---|---|---|---|
| `snapshot_date` | Date | Yes* | Immutable after creation. Exactly one snapshot per page has no date — that's the initial snapshot. If None, `actual_transactions`/`expected_transactions`/`earmark_events` are all empty. |
| `full_amount` | Float | Not immediately | The account balance *after* all of that day's transactions. Starts as None; set by a cascade once the date is today-or-earlier — the very first value a cascade sets. Computed as yesterday's `full_amount` + today's `actual_transactions` sum. |
| `expected_amount` | Float | Not immediately | Yesterday's `expected_amount` (or `full_amount`, if set) + today's `ExpectedTransaction` amounts. |
| `expected_free_amount` | Float | — | The forward-looking estimate of `full_amount` net of fund jars — but, unlike `current_free_amount`, it can *never* factor in unfulfilled/unpaid bills, because cascade-computed values can't depend on values that themselves require a non-cascading, dynamic calculation. |
| `fund_jars` | `FundJar[]` | — | Must include exactly one jar with `finance_id = None` (the safety cushion), and all others must have unique `finance_id`s. |
| `actual_transactions` | `ActualTransaction[]` | — | All must have `occurred_date == snapshot_date`. |
| `expected_transactions` | `ExpectedTransaction[]` | — | All must have `expected_date == snapshot_date`. No two may share a `finance_id`. |
| `earmark_events` | `EarMarkEvent[]` | — | All must have `earmark_date == snapshot_date`. If an isolated earmark and a repeated earmark of the same `finance_id` both land here, the isolated one's `actual_amount` must be None. |

### FundJar
A named bucket of money set aside for a goal (or the safety cushion, if `finance_id` is None). Can never be created directly by a user — only ever as a side effect of an `EarMarkEvent`.

> "-----responsiblities (what should this class facilitate?)
> Used for setting money aside (recording that the money is set aside without moving it to another account) for big expenses. Keeps track of
> 1: how much money we have set aside,
> 2: what the money is set aside for
> 3: how much money should we have set aside at this point.
> The user should be warned if they are falling behind on setting money aside for a goal." — `class documentation.ods` *(verbatim, sic — replaces an earlier condensation of this quote that dropped its most load-bearing clarification: a jar records that money is set aside **without moving it to another account**. It's bookkeeping over one account's balance, not a transfer.)*

| Property | Type | Mandatory | Meaning |
|---|---|---|---|
| `finance_id` | Int | Yes | The goal this jar is saving for. None ⇒ this is the safety-cushion jar (and it never gets a `milestone_amount`). |
| `current_amount` | Float | — | How much is actually in the jar as of this date. Starts as None; set by a cascade once the date is today-or-earlier. Never goes below 0. A change in priority does *not* retroactively reshuffle money already sitting in jars — it only affects future allocation. The ODS description trails off mid-thought, verbatim: "After full_amount is set, ....?" — the author's own unresolved question about the exact computation order, left unanswered in the source. |
| `expected_amount` | Float | Not immediately | Yesterday's `expected_amount` (or `current_amount`, if set) + today's same-`finance_id` `EarMarkEvent` amounts. |
| `milestone_amount` | Float | — | How much *should* be saved by this date — the running sum of expected values of repeated earmarks up to and including today. Never set for the safety-cushion jar. |

There is also a special **initial, dateless FundJar** per `AccountTransactionPage`/`initial_snapshot`: it holds the starting balance for the period, has no date, can't be altered by events within its own period, and must carry the `finance_id` so later same-period jars can build off it (see the `fund jar` scratch sheet in the ODS for eight hand-worked timeline scenarios around this).

**"Need to see in past / present / future" flags** *(added 2026-07-10 — structured display metadata from the ODS Properties sheet, present on only five properties and previously not carried into this doc; directly relevant to which computed values the UI must surface, and for which time range)*:

| Property | Past | Present | Future |
|---|---|---|---|
| `EarMarkEvent.expected_amount` | yes | yes | yes |
| `EarMarkEvent.actual_amount` | no | yes | yes |
| `BalanceSnapshot.full_amount` | no | yes | yes |
| `BalanceSnapshot.expected_amount` | no | no | yes |
| `BalanceSnapshot.expected_free_amount` | no | no | yes |

## Conceptual groupings that aren't classes

The earliest XML sketch (`fakexmltest.txt`, March 2021) and the `planning.txt` responsibility outline (July 2021) both organize `AccountTransactionPage`'s contents under intermediate grouping labels that **did not survive as classes** in the final design (`class documentation.ods`, Jan 2022, defines exactly the 10 classes above — and that matches what's actually implemented in `classes/*.py`). They're worth knowing about only because you'll see them mentioned in the older notes and pseudocode:

| Early grouping label | What it became |
|---|---|
| `EventPlanner` | Just a label for "`finance_patterns` + `earmark_patterns` together," both of which live directly on `AccountTransactionPage`. |
| `EarmarkEvents` (container) | The `earmark_events` list inside each `BalanceSnapshot`. |
| `PairedTransactions` / `TransactionPair` | Never became its own join-object class — implemented instead as **mirrored fields** on `ExpectedTransaction` (`paired_amount`, `paired_actual_date`) and `ActualTransaction` (`paired_finance_id`, `paired_expected_date`) that must all agree for the pair to be valid. |
| `LooseTransactions` | Not a type — a *state*. An `ActualTransaction` is "loose" simply when its pairing fields are unset. |
| `BalanceRecord` | Survived, but as a property (`AccountTransactionPage.balance_record`, a `{Date: BalanceSnapshot}`), not a class. |

## Domain vocabulary

**Assumption** — a mathematical guarantee about program state, given a dotted numeric ID like `3.13b.a8` (see [03-assumptions-glossary.md](03-assumptions-glossary.md) for the full ID grammar and catalog). Assumptions form a dependency graph: some can only be true once others are already true.

**Self-valid** — a class instance that satisfies every assumption listed under its class. If instance A derives a value from instance B, B is assumed self-valid first; if a self-valid P requires a non-None property of type C, that C instance must itself be self-valid before P can be.

**Cascade / cascade update** — the forward-only recalculation that walks a page's `balance_record` from the last known-good date to the present (`cascade_page_balance_record`). Hard rule from `planning.txt`: any value touched by a cascade may only be derived from (a) other classes' values *on the same date*, or (b) the *same class's* value on the previous date — never from anything later.

**Casc-updateable** — an instance variable that a cascade update changes. Per `planning.txt`, this should only exist if it's (1) needed to compute the next step of the cascade, or (2) something worth showing the user persistently — the author was explicitly wary of holding onto more state than necessary.

**Deallocation day** — a day where total actual transactions exceed the free funds available, forcing the system to implicitly pull money back out of fund jars (via negative implicit isolated earmarks) to cover the gap.

**Repeated vs. isolated earmark** — repeated = spawned by an `EarMarkPattern`'s rrule, amount fixed by the pattern; isolated = manual or system-generated one-off, amount mutable. At most one of each per `finance_id` per day; a second isolated earmark for the same `finance_id`/day just merges into the first.

**Implicit vs. explicit amount** — `explicit_amount` on an isolated `EarMarkEvent` tracks only what the *user* actually entered, so the system can later undo an implicit (automatic) adjustment without losing the user's original intent.

**Milestone amount** — how much a `FundJar` *should* contain by a given date (sum of expected repeated-earmark contributions to date). Compare against `current_amount`/`expected_amount` to see if a goal is falling behind.

**Safety cushion / safety balance** — money held in reserve, modeled as a `FundJar` with `finance_id = None`. Per `planning2simple.txt`, conceptually acts like "a fund jar with priority 0": always last in line for free funds, first in line to have funds pulled back out.

**Priority** — an integer on `FinancialPattern`, `EarMarkPattern` (inherited from the goal's pattern), and the account's safety balance. Governs funding order when money is short. No two competing priorities may tie.

**Mandatory** — flags a `FinancialPattern` as a bill that must be paid (auto-defaults true for negative amounts); mandatory bills always outrank non-mandatory ones for priority purposes.

**Pairing / Fulfillment** — matching an `ActualTransaction` to the `ExpectedTransaction` it satisfies. Valid only when all four mirrored fields agree: `ExpectedTransaction.paired_amount == ActualTransaction.amount`, `ExpectedTransaction.finance_id == ActualTransaction.paired_finance_id`, `ExpectedTransaction.paired_actual_date == ActualTransaction.occurred_date`, `ExpectedTransaction.expected_date == ActualTransaction.paired_expected_date`.

**Deviation** — when a paired actual transaction's amount or date falls outside its expected transaction's `amount_tolerance`/`date_tolerance` — surfaced to the user as a warning instead of a plain checkmark.

**rrule / date_pattern** — a `dateutil` recurrence rule driving `FinancialPattern`/`EarMarkPattern` generation. See the `dateutil.rrule` research links in `project goals.txt.txt`.

**Source** — the string a `FinancialPattern`/`ActualTransaction` is matched against in bank/Mint data, for automatic pairing.

**Finance ID (`finance_id`)** — the key that threads one goal or bill through `FinancialPattern` → `ExpectedTransaction` → `EarMarkPattern` → `EarMarkEvent` → `FundJar`. Even a one-off, manually-created "isolated" expected transaction gets a synthesized `FinancialPattern` so it still has one.

**Expired page** — an `AccountTransactionPage` that can no longer be edited; nothing can cascade outside it. `force_expire()` also severs (without deleting) any pairing that reached across into now-frozen data.

**Page length** — `TransactionLogBook.page_length`, the number of months each `TransactionLogPage` spans.

**Instance-scope suffixes (b / c / f / p / n)** — from the assumption-ID grammar in `planning2simple.txt`: lowercase letters appended to a property number to scope a rule to specific list members — `c` (Current) for a single reference instance, plus Before/Current/Following/Previous/Next variants — most often used to distinguish "this page" from "the page before/after it" in the log book. Capitalized forms (`B`/`C`/`F`/`P`/`N` or spelled out) scope a rule to *all* matching instances rather than one. `x` marks an ID nobody has assigned yet.

**UC (use case)** — a scenario-anchored bundle of assumptions, e.g. `UC.0.1`: "we have an empty TransactionLogBook — we don't even have dates or a page yet." Used as worked starting points in `planning2simple.txt` rather than as a systematic catalog.

**Show / Warn / Maintain / Plan** — the four top-level feature categories from `planning.txt`/`planning2simple.txt`'s product brainstorm: *Show* = answer a question the user comes looking for; *Warn* = proactively surface something important (low funds, deviations, goal risk); *Maintain* = keep the transaction/pairing records accurate, mostly automatically; *Plan* = help the user work out how to reach a savings goal.

## Naming quirks & open questions

These are worth knowing about before treating any single source as gospel:

- **`TransactionLogPage` bounds were renamed.** `fakexmltest.txt` (Mar 2021) uses `last_date` and `archived`; every later source uses `end_date` and `expired`. If you see `last_date`/`archived` anywhere else, treat it as the old name.
- **`EarMarkEvent` vs. `EarmarkEvent` vs. "earmark."** Capitalization is inconsistent across sources (`a02.txt` heads a whole section `EarmarkEvent:`), but the ODS explicitly states "earmark" and "earmark event" are the same concept. The class name in `classes/EarMarkEvent.py` is the one to trust.
- **`FinancialPattern`'s property numbering doesn't match between the assumption files and the ODS.** `a02.txt` asserts `4.1.a1` = "finance_id cannot be None" and `4.2.a1` = "source cannot be None," implying `finance_id`/`source` were properties #1/#2. The ODS (much later) instead numbers them `4.5`/`4.9`, with `amount` as `4.1`. Likely explanation: `FinancialPattern` grew from 2 properties to 10 between Aug 2021 and Jan 2022, and the ID scheme reflects insertion order into a working spreadsheet rather than a stable position. **When reconciling assumption IDs against the ODS later, don't assume the numeric suffix means the same property in both.**
- **`ActualTransaction` has a similar, smaller drift**: `a02.txt`'s `6.1.a1` asserts `source` cannot be None, but the ODS's ID column pairs `6.1` with `occurred_date` and `6.2` with `source`. Same caveat applies.
- **`EarMarkEvent`, `BalanceSnapshot`, and `FundJar` show a consistent off-by-one between their ODS class-number column and their property-ID prefix** (e.g. `EarMarkEvent` is listed as "class 8" but its properties are prefixed `9.x`; `BalanceSnapshot` is "class 9" with properties prefixed `10.x`; `FundJar` is "class 10" with properties prefixed `11.x`). The assumption files consistently use the *class-number* value as the property prefix instead (`8.1.a1` for `EarMarkEvent.finance_id`, etc.) — that's the scheme actually used everywhere assumptions are written down, so it's the one used throughout this glossary and in [03-assumptions-glossary.md](03-assumptions-glossary.md).
- **`ExpectedTransaction.paired_amount`/`paired_actual_date` vs. `ActualTransaction.paired_finance_id`/`paired_expected_date`** are easy to transpose when reading the older notes — they are deliberately named from each side's own perspective, not symmetric names for the same field. See [Pairing / Fulfillment](#domain-vocabulary) for the exact cross-mapping.
- **`current_unpaid_expected` (`AccountTransactionPage` property 6)** is never asserted directly as a `3.6.aX` assumption anywhere in `a01`/`a02`/`a03` — it only shows up indirectly via the longer path form `1.2.3.6.a1`. Not a contradiction, just a documentation gap worth knowing about if you go looking for a `3.6.*` assumption and can't find one.
- **`things to test.txt`** (project root, not read in depth per the requested scope) looks like it may be a later revision of the "things to test" section already captured inside `planning2simple.txt`. Worth a quick diff before relying on either exclusively.
