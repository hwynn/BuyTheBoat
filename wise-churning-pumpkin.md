# Restructure the C# rewrite onto the original class organization scheme

## Context

The lean `ForecastCalculator` rewrite answers Q1/Q3 but abandoned the original design's organizational spine (TransactionLogBook → TransactionLogPage → AccountTransactionPage → BalanceSnapshot → FundJar/EarMarkEvent/ExpectedTransaction), leaving Q2 with no home, the output split across two disconnected grids, and the allocation mechanism mislabeled as "one-time goals only." The user (author of the original design docs) has ruled: bring the original classes back as human-readable data structures, compute their values with a day-by-day cascade under a new standing philosophy — **assumed pairing** (treat every expected transaction as if its matching actual transaction will occur; decisions that would wait for pairing are made now) — and unify the output into one TransactionLogPage display. Deallocation/safety-cushion/priority-reallocation is explicitly the NEXT pass, built on these structures.

User's scope decisions: **structures first** (no deallocation engine this pass) · **in-memory per run** (no persistence changes) · **day table + detail pane** display · **one TransactionLogPage per forecast window** (fixed page_length/runoff deferred).

## Architecture

All new types in `MyMoneyForecast.Domain` (`redesign/MyMoneyForecast/src/MyMoneyForecast.Domain/`). Persistence layer untouched. Patterns + CurrentBalance remain the only stored truth; each Forecast click builds the full structure fresh (same stateless philosophy as today's `ForecastCalculator`, which these types replace).

### Cascade algorithm (documented-faithful under assumed pairing)

Key mapping insight: since AsOfDate = "today" and everything forecast is future, the whole current engine maps onto the docs' **expected_*** family; `FullAmount`/`CurrentAmount` stay null for future dates *exactly as documented* — not a divergence.

1. **Materialization (`AdjustSnapshots` role):** precompute occurrences per pattern once (perf — 15-yr test guards). Snapshot exists exactly on dates with ≥1 event in window. Events: ExpectedTransactions from FinancialPatterns; repeated EarMarkEvents from EarMarkPatterns; implicit isolated EarMarkEvents generated for (a) goal-occurrence jar withdrawals (−|goal.Amount| on the goal's expected date — this is `3.13c.a10`'s assumed-pairing form, matching current `JarBalanceAt` withdrawal), and (b) **auto-bill reservations**: per `GetAutomaticallyEarmarkedBills` bill, on each snapshot date an implicit isolated event adjusting that bill's jar to the current `BillAccrualAt` target (ramp + snap-to-full + reset-on-due preserved exactly — accrual only ever mattered at snapshot dates). Positive implicit earmarks contradict the original "implicit isolated earmarks are only ever negative" — user-endorsed divergence (#8), tag it.
2. **Initial snapshot** (dateless, per docs): FullAmount = entered balance; ExpectedAmount = FullAmount; jars seeded with pre-AsOfDate state (StartingAllocation + earmark occurrences before AsOfDate − goal withdrawals ≤ AsOfDate — current `JarBalanceAt(AsOfDate)` logic relocated; auto-bill jars at their AsOfDate accrual); CurrentAmount = ExpectedAmount (assumed pairing, tag); ExpectedFreeAmount = ExpectedAmount − Σ jar ExpectedAmounts.
3. **Value pass (`CascadePageBalanceRecord` role)**, chronological, each snapshot from the previous (user requirement #6 — true cascade):
   - `ExpectedAmount = prev.ExpectedAmount + Σ(today's ExpectedTransactions)` (10.3). AsOfDate-dated occurrences excluded from the sum (seed balance already includes that day — current convention, tag).
   - Per jar: `ExpectedAmount = max(0, prev jar + Σ(today's EarMarkEvents for that id))` (3.13.5.3.a1); `MilestoneAmount` = Σ repeated-earmark amounts from pattern start → date (3.13.5.4.a1); cushion jar stays 0/no-milestone.
   - `ExpectedFreeAmount = ExpectedAmount − Σ(jar ExpectedAmounts)` (3.13.4.a1) — equals today's FreeBalance. (Follow the assumption's formula, NOT the archived Python's accumulator variant — that code is flagged buggy.)
   - FullAmount/CurrentAmount = null (future).
4. **Summaries:** GoalShortfalls (unchanged math), JarLabels, negative-free detection over ExpectedFreeAmount.
